# @deepseek-ai/dsh-shell-command

[English](README.md) | 中文

针对已组合的 `ctx.shell` 能力缝执行人类 `!` shell 命令，并在接收会话的日志上记录持久的 `shell/run`/`shell/done` 生命周期。

## 服务契约

`ctx.shellCommand.run(agent, command, signal)` 针对会话的 agent 执行一条以 `!` 为前缀的 composer 行。网关将线上的会话身份解析为精确存活的 `Agent`；服务会去除前导 `!` 后的内容并校验非空，然后通过 `ctx.shell.resolve()`/`ctx.shell.run()`（在 `tool` 模式下是 `ctx.shell.start()`）执行——与模型使用的 bash/pwsh 工具共用同一个执行器，因此执行器配置的超时、输出上限和环境处理保持不变。命令在会话的工作目录（存在 `agent.session.header.cwd` 时）中、在该会话解析出的沙箱策略下运行，与模型 shell 工具的行为完全一致。

生命周期作为仅日志的一对事件记录在接收 agent 的会话上：`shell/run`（执行前，包含铸造的 `commandId`、修剪后的命令、发出来源，以及已知时的工作目录）和 `shell/done`（结束时，包含结果类型、结构化的 `exitCode`/`signal`/`timedOut` 和有界的合并 stdout/stderr `output`）。两者都是直接的独立追加：没有轮次包裹它们，持久化通过普通检查点和关闭时排空。空命令以错误结果结束且不记录任何内容。

## 执行模式

`mode` 配置选择一条 `!` 行的执行方式：

- `direct`（默认）：一次性同步执行。命令在前台运行到完成，结果仅在结束之后以单条用户消息报告给 agent。这是历史行为。
- `tool`：命令立即作为 `ctx.jobs` 拥有的后台任务启动，并立即向 agent 发送一条描述正在运行任务的用户消息。`run` RPC 立即返回（永远不会阻塞在命令上），机器可以通过面向模型的 `job_output`/`job_kill` 工具在其生命周期内检查、等待或停止该任务。`shell/done` 卡片随任务最终进程结果结束，因此人类 UI 终端块得以保留，输出也会在任务结束时到达模型的下一次请求。

`tool` 模式需要一个已组合的 `ctx.jobs` 注册表（例如 `jobs-local` 行），缺少时会在这条 `!` 行上明确失败。

## 组合

随附的 `dsh web` bundle 挂载此服务（host 平面）和 `ui-shell-command` 客户端插件，后者注册 `!` 输入触发源和 `shell-command` 聊天节点。该服务需要一个已组合的 `ctx.shell` 执行器（base 的 `bash-sandbox`/`pwsh-sandbox` 行）；没有执行器的组合会在加载时失败。

## 模型体验

### 直接人类 shell 命令

#### 模型看到什么

在 `direct` 模式下，什么也没有。`!` 行由客户端的输入触发源拦截并在 shell 命令平面执行；命令文本及其输出都不会在执行时作为用户消息提交或以其他方式到达模型请求——结束的命令会在之后作为用户消息报告。`shell/run`/`shell/done` 事件仅用于日志，永远不会直接呈现给模型。在 `tool` 模式下，模型会为每条 `!` 行看到一条命名正在运行的后台任务（`job_output`/`job_kill` 可用于检查或停止它）的用户消息。完整命令输出只有在该模式读取任务时才会到达模型。

#### Token 影响

`direct` 模式为每条已结束的 `!` 行增加一条用户消息。`tool` 模式为每个启动的任务增加一条用户消息（任务启动提示）。

#### KV 缓存影响

两种模式都会将各自的单条用户消息加入请求缓存；命令输出本身只在该模式通过 `job_output` 读取任务时才进入模型请求。

## 已知限制和待办工作

- **`direct` 是一次性前台执行**——每条 `!` 行都在全新进程中运行；命令之间不保留状态（cwd、变量、函数）。
- **`tool` 将生命周期交给模型的 job 控制**——任务在后台运行，输出通过 `job_output` 消费，因此长时间运行的命令在结束之前会保持为运行中的卡片。
- **`direct` 无流式输出**——输出在命令结束时捕获并显示；长时间运行的命令在此之前显示为运行中。
