# Agent Note: Android 配对先提交，再进行可选通知设置

Status: implemented

[English](2026-08-30-android-pairing-commits-before-notification-setup.md) | 中文

## 问题

Android 配对可能已在主机成功，App 却仍停留在连接界面。App 在存储配对配置并切换路由之前等待通知权限与前台服务设置，尽管这两项操作都不建立 GUI 访问。手动配对还会存储空的 GUI 访问令牌，因为只有二维码载荷包含该令牌；iframe 随后在没有请求鉴权的情况下加载并进入重连流程。

## 决策

主机的 `paired` 回复携带设备 id、设备密钥和持久 GUI 访问令牌。二维码与手动配对都从该已鉴权 WebSocket 回复取得 GUI 鉴权信息，因此两个入口生成相同的持久配置。

配对回复通过协议校验后，App 会存储完整配置并切换到已连接路由。`ConnectedScreen` 在挂载时启动前台服务，也会处理恢复的会话；通知权限请求则在配对后独立运行。通知调用悬起或被拒可能抑制 Android 提醒横幅，但不能延迟 GUI 访问或让其失效。

## 已否决的替代方案

**只在二维码载荷中保留 GUI 令牌。** 否决：手动输入仍会生成有效设备密钥，但 iframe 未经鉴权，使公开的备用入口不完整。

**等待通知设置并添加超时。** 否决：超时仍会延迟主流程，并为可选功能选择任意失败阈值。

**先导航，再持久化配对配置。** 否决：导航后若进程终止，会在一次性配对令牌已消耗后丢失有效设备密钥的唯一副本。

## 后果

- 持有有效一次性配对令牌即可获发设备通道与 GUI 凭据。配对令牌和 `paired` 回复都必须保密。
- GUI 导航只依赖配对握手和持久配置写入。通知设置可以恢复，并在已连接界面挂载时重试。
- Android 设备冒烟测试服务器要求 GUI 请求提交访问令牌，避免设备握手成功掩盖 iframe 登录损坏。

## 测试

主机通道和网关测试覆盖扩展后的回复以及 GUI 令牌一致性。Android 类型检查、单元测试、生产资源构建、Capacitor 同步与调试 APK 组装均通过。在 Android 模拟器上，手动配对会在尚未授予通知权限的对话框完成之前到达已连接路由，mock PC 也会记录已鉴权 GUI 请求。预授权设备测试覆盖配对、持久化、断开、清除与错误流程。
