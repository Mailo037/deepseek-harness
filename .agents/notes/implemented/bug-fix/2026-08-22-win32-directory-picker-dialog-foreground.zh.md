# Agent Note：将 Win32 目录选择对话框提升到浏览器之上

Status: implemented

[English](2026-08-22-win32-directory-picker-dialog-foreground.md) | 中文

## Problem

在 Web GUI 中点击「Add workspace」在 Windows 上看起来毫无反应：没有选择器、没有任务栏条目、也没有错误。RPC 链路端到端都是通的，驱动也成功 spawn 了 koffi worker，但两种原生结果都会让 UI 一直处于等待状态：`IFileOpenDialog::Show` 可能在最大化浏览器后方创建一个没有任务栏条目的对话框，也可能在完全没有创建公共对话框窗口的情况下阻塞。Windows 只把前台权限授予用户最后交互的进程，而选择请求经 RPC 到达的是后台服务进程。worker 的 `showing` 通知先于 `Show`，所以它只证明 COM 调用即将开始，不能证明窗口已经存在。

## Decision

驱动在收到 `showing` 通知后启动一个有预算的串行提升服务（`raiseThreadWindows`，与现有中止杠杆 `closeThreadWindows` 并列）。它会重试，直到可见的 `#32770` 公共对话框被抬起，或每次探测都报告该窗口不存在。两个服务都声明匿名 Koffi 回调原型，因为 Koffi 会拒绝它们在第二次尝试时重新声明同名类型。`IFileOpenDialog` 会先于真正对话框创建工具类和非工具类辅助窗口；提升器会识别公共对话框类并忽略所有辅助窗口，因此 tooltip、自动建议弹窗或其他瞬态窗口不会提前结束重试。成功的尝试会将对话框在其整个生命周期内固定为 `HWND_TOPMOST`，并添加 `WS_EX_APPWINDOW` 为无属主的对话框提供任务栏条目；随后通过 `AttachThreadInput` + `SetForegroundWindow` 尽力争取键盘焦点。如果每次探测都成功完成却没有找到公共对话框，驱动会终止阻塞的 worker，等待它退出，并完整重试一次 COM 会话。第二次仍没有窗口时，选择请求会以失败结束。探测失败仍按尽力而为处理：驱动无法区分检查失败与窗口已存在，因此既不会终止也不会重试该 worker。真正的提升只在 win32 上经懒加载的 koffi 绑定运行；驱动的测试通道为两个杠杆注入 fake。

## Alternatives considered

**给 `Show` 一个来自浏览器或服务进程的 owner 窗口。** 否决：两个进程都不拥有对话框线程上的窗口，跨进程 owner 对公共对话框而言属于不受支持的区域。

**在 Worker 内、`Show` 之前做提升。** 否决：对话框窗口要等 `Show` 创建它才存在，而 worker 正阻塞在该调用内——不存在「窗口既已创建又可达」的时机。

**模拟 Alt 按键绕过前台锁。** 否决：它操纵全局键盘状态去赢取焦点，而 topmost 切换不需要任何权限就能做到。

**激活失败时回退到 browse 后端。** 否决：激活不是能力故障——系统选择器本身正常，错的只是它的 z-order。组合层面的回退会因为一次外观上的拒绝而惩罚所有宿主。

**在公共对话框窗口不存在时无限重试。** 否决：持续性的 shell 或 COM 故障会造成无界的进程循环。一个新 worker 足以恢复一次瞬态会话失败；第二次仍无窗口时会转为显式失败。

## Consequences

无论哪个进程持有前台，一次选择都会把选择器固定在所有非 topmost 窗口之上并为其显示任务栏条目。辅助窗口保持不变，也不会停止有预算的探测。公共对话框窗口缺失会付出一次有界探测和一次自动重试；两次都缺失时会拒绝请求，而不会让调用方一直等待。固定持续到对话框生命周期结束；选择的结算路径会关闭窗口。焦点争取仍受前台锁约束：在某些宿主上，对话框被固定显示但没有键盘焦点，用户的第一次点击用于聚焦它。驱动测试覆盖恢复和重复缺失，win32 真实对话框冒烟测试会经过真正的提升器，绑定测试则拒绝把工具类和非工具类辅助窗口算作成功提升，并在单个进程中执行重复回调。
